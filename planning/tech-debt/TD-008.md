Decision sources (direct product-owner instruction, 2026-09-21): `docs/final-decisions.md` — "Product-owner responses to MVP-005 open items" (section B) and "Product-owner decisions for MVP-021" (Q28). Open questions 6 (part 2), 27 and 28.

**This is a separate, small corrective change. It is not part of MVP-021 and must not be folded into it.** It must land **before MVP-012 permits creators or administrators to write compatibility evidence** through the product editor. It is not marked complete by any other story.

## 1. Current schema inconsistency
Merged MVP-005 implements the earlier three-state vocabulary:
1. **Enum** `CompatibilityEvidenceStatus` = `TESTED`, `CREATOR_DECLARED`, `NOT_VERIFIED`. There is **no `MARKETPLACE_REVIEWED`** value and **no reviewed-at column** on `compatibility_records`.
2. **Validator** `validateCompatibilityEntry` accepts `TESTED` and `NOT_VERIFIED` as ordinary assignable statuses.
3. **Presentation:** the on-page legend (`EVIDENCE_LEGEND`) defines Tested, Creator Declared and Not Verified; it would display "Tested" as soon as any compatibility row exists. The Creator Declared definition differs from the approved wording.
4. **Tests** assert the old vocabulary (`compatibility.test.ts`, `present-evidence.test.ts`, `product-evidence.test.tsx`; and the constraint tests in `catalog-repository.integration.test.ts`, which use `TESTED` to prove the "Tested requires evidence" CHECK).
5. **Docs** (`packages/domain/catalog/README.md`, the MVP-005 progress-report entry) describe the old vocabulary.

No user-visible harm exists today: there are no product or compatibility rows and nothing can write them (TD-006).

## 2. Approved assignable statuses
- **Creator Declared** — supplied by the creator; not independently certified by the marketplace.
- **Marketplace Reviewed** — a moderator reviewed the statement for completeness, plausibility, prohibited claims and publication readiness. It is a **per-claim evidence status**. It does not mean independently tested, certified, guaranteed, Microsoft approved/certified, officially supported or verified compatible.
- **Tested — reserved:** not assignable, never inferred, never migrated to, no badge or filter; not removed destructively.
- **Not Verified — not assignable and not a third choice.** Unreviewed information is Creator Declared. Absent information shows the approved empty state and **no Not Verified record is created**.

## 3. State-transition rules
| From | Actor | To | Notes |
|---|---|---|---|
| (new claim) | creator (owner of the product) | `CREATOR_DECLARED` | the only status a creator may set |
| `CREATOR_DECLARED` | creator | `CREATOR_DECLARED` | ordinary edits |
| `CREATOR_DECLARED` | moderator (server-side moderation workflow) | `MARKETPLACE_REVIEWED` | sets `reviewedAt` |
| `MARKETPLACE_REVIEWED` | creator makes a **material** change | `CREATOR_DECLARED` | clears `reviewedAt` — unless an approved moderation design specifies another transition |
| any | anyone | `TESTED` or `NOT_VERIFIED` | **rejected** (reserved / legacy) |

**Not decided — needed from MVP-013's moderation design, not invented here:** (a) which edits are "material" (proposal to confirm: any change to platform area, minimum release year/wave, notes or evidence summary; whitespace-only normalization is not); (b) whether a moderator may withdraw a review, and to what state; (c) administrator authority over compatibility evidence (default until decided: no more than a moderator, and never `TESTED`).

## 4. Reviewed-timestamp behavior
- Column `reviewedAt`, nullable `DateTime`, named per repository convention (`publishedAt`, `lastVerifiedAt`).
- **Null for Creator Declared** claims; **set only when a claim transitions to Marketplace Reviewed.**
- Assigned **only by the trusted server-side moderation workflow**, using the server clock. It is **never accepted from a creator or an ordinary client request**: it is absent from creator-facing request schemas and any client-supplied value is ignored or rejected.
- Returned to null when a reviewed claim reverts to Creator Declared (section 3).
- **Never fabricated for existing records.** No existing row can be Marketplace Reviewed today, so there is nothing to backfill.
- Proposed database rule: `("evidenceStatus" = 'MARKETPLACE_REVIEWED') = ("reviewedAt" IS NOT NULL)`, so the two cannot drift apart.
- **Moderator identity / review reference (proposal only — not added):** the moderation entities (`ModerationReview`, `ModerationComment`, `AuditEvent`) are named in `docs/06-data-model.md` and `docs/09-marketplace-operations.md` says a decision captures "reason code, narrative, evidence, reviewer and timestamp", but **none of them exists in the schema yet** (MVP-013 builds them). So the reviewer identity should live on `ModerationReview` and the audit trail on `AuditEvent`; a `moderationReviewId` reference on the claim should be considered by MVP-013 once that table exists. Not added now.
- **Public display of the reviewed date — undecided.** The "Last Verified" column must not carry it (review is not verification). Any new wording ("Reviewed on …") is a content decision needing product-owner approval.

## 5. Legacy or reserved values (`NOT_VERIFIED`, `TESTED`)
- Never removed destructively (Postgres cannot drop an enum value without a table rebuild in any case).
- **Not silently converted.** Before any conversion, inspect provenance per environment: `SELECT "evidenceStatus", count(*) FROM compatibility_records GROUP BY 1;` — expected to return no rows today (verified empty on the dev database at MVP-005; CI databases are ephemeral).
- If legacy rows are found, the product owner reviews provenance before any conversion. Until reviewed, **fail closed:** legacy reserved values are not shown in the public matrix and the legend does not define Tested. (To be confirmed with the product owner when the change is scheduled.)
- The existing "Tested requires evidence summary and verified date" CHECK stays: it remains correct for the reserved value.

## 6. Authorization requirements (server-enforced, deny by default)
- Creators may create and edit compatibility claims **only for their own products** and **only as Creator Declared**.
- Only the trusted moderation workflow, for an authorized moderator, may set Marketplace Reviewed and `reviewedAt`. Creators cannot assign Marketplace Reviewed; moderators cannot assign Tested; nobody can assign Not Verified.
- No client-supplied status, `reviewedAt` or reviewer field is trusted.
- Every transition emits an audit event (`AuditEvent`, MVP-019 scope) and a telemetry log without secrets or claim text.

## 7. Migration and backward-compatibility approach
1. **Migration A (additive):** `ALTER TYPE "CompatibilityEvidenceStatus" ADD VALUE 'MARKETPLACE_REVIEWED'` in its **own** migration — a newly added enum value cannot be referenced in the same transaction.
2. **Migration B (additive):** add `"reviewedAt" TIMESTAMP(3)` (nullable) and the CHECK above. Hand-written, with a rehearsed rollback (drop the column and constraint; the enum value cannot be dropped and is harmless).
3. Never drop `TESTED` or `NOT_VERIFIED`. No data migration unless the inspection query above finds rows, and then only after provenance review.
4. Code: validator (`TESTED`/`NOT_VERIFIED` rejected as reserved/legacy; the two approved statuses accepted), display model and legend (Creator Declared and Marketplace Reviewed with the approved definitions), and the read model tolerating legacy values without displaying them.
5. Existing pages remain valid at every step; the empty state is unchanged.

## 8. Tests required
- **Validator:** a creator-context call accepts only `CREATOR_DECLARED`; `TESTED` and `NOT_VERIFIED` are rejected; `reviewedAt` is not accepted from input.
- **State transitions:** create → Creator Declared; moderator review → Marketplace Reviewed with `reviewedAt` set; material creator edit → Creator Declared with `reviewedAt` cleared; a non-material edit leaves the review intact (per the confirmed definition).
- **Authorization:** creator cannot set Marketplace Reviewed or `reviewedAt`; moderator cannot set Tested; a non-owner cannot edit; unauthenticated is denied.
- **Database (integration, DB-gated):** the `reviewedAt` ↔ status CHECK rejects both mismatches; the existing "Tested requires evidence" and range constraints still hold; the enum accepts the new value.
- **Presentation:** legend lists exactly Creator Declared and Marketplace Reviewed; Tested and legacy values never render; the empty state is unchanged; no certification-style wording anywhere.
- **Migration:** rollback rehearsal; inspection query returns the expected rows.
- **Audit/telemetry:** each transition emits its event.

## 9. Dependency on MVP-012 and MVP-013
- **Hard gate for MVP-012:** the creator/administrator product editor must not expose any compatibility-status write until TD-008's vocabulary and role rules are in place. Until then MVP-012's acceptance criteria are limited to Creator Declared.
- **MVP-013** supplies the moderation workflow that sets Marketplace Reviewed and `reviewedAt`, the `ModerationReview`/`AuditEvent` entities, and the decisions marked "not decided" in section 3.
- Depends on TD-006 (the write path must call `validateCompatibilityEntry` and screen for private data).

## Risk if left unresolved
Once any compatibility row exists the legend tells buyers what "Tested" means although no product can be Tested, and a moderator-assigned Marketplace Reviewed cannot be stored. Once write paths exist, creators could be offered a status the decision prohibits.

## Resolved by (story/commit, once closed)

**Partially resolved 2026-09-24**, own branch (`tech-debt/td-008-evidence-vocabulary`), per direct product-owner instruction ("Do not build the write path — TD-006 and MVP-012 own that"). Section 7's migration/code plan is implemented in full; the write path, moderation workflow and role enforcement (sections 3, 6, and the `ModerationReview`/`AuditEvent` entities section 4 names) remain entirely unbuilt, owned by MVP-012/013 as this record always said.

**What landed:**
- Migration A (`20260924000000_add_marketplace_reviewed_status`): additive `MARKETPLACE_REVIEWED` enum value, its own migration (Postgres cannot reference a newly added enum value in the same transaction that adds it).
- Migration B (`20260924010000_add_compatibility_reviewed_at`): nullable `reviewedAt` column plus the CHECK constraint `("evidenceStatus" = 'MARKETPLACE_REVIEWED') = ("reviewedAt" IS NOT NULL)` — the two can never drift apart. Verified against a real database, both directions: a `MARKETPLACE_REVIEWED` row without `reviewedAt` is rejected, a `reviewedAt` set on any other status is rejected, and a correctly-paired row is accepted.
- `TESTED`/`NOT_VERIFIED` untouched, not removed, not migrated to (section 5) — confirmed by keeping every existing "Tested requires evidence" CHECK-constraint rejection test passing unchanged.
- `validateCompatibilityEntry` (`@ppu/domain-catalog`) now accepts only `CREATOR_DECLARED`/`MARKETPLACE_REVIEWED`; `TESTED`/`NOT_VERIFIED` are rejected with a distinct `EVIDENCE_STATUS_RESERVED_OR_LEGACY` code, regardless of what else is supplied (the old "Tested requires an evidence summary and date" special case is now unreachable application-side and was removed — the database CHECK still enforces it for the reserved value directly). `reviewedAt` was never an accepted input field and stays that way — nothing added it.
- `EVIDENCE_LEGEND` (`present-evidence.ts`) now lists only the two assignable statuses, in the approved wording (`docs/final-decisions.md`, 2026-09-21, section B) — verbatim, not paraphrased. `presentProductEvidence` filters `TESTED`/`NOT_VERIFIED` rows out of the public compatibility matrix entirely (fail closed, section 5) — a dedicated regression test proves this.
- `docs/06-data-model.md` and `packages/domain/catalog/README.md` updated to describe the real, corrected vocabulary instead of the pre-2026-09-21 one.

**What did not land, deliberately (as of 2026-09-24, before MVP-012):** any write path (creator or moderator), the `ModerationReview`/`AuditEvent`/`moderationReviewId` entities, authorization enforcement (section 6), the state-transition rules as enforced code (section 3 — the pure `isValidArticleStatusTransition`-style check for evidence status does not exist yet, since nothing writes evidence yet), and the legacy-row inspection query (section 5) — no rows exist to inspect, so it was not run against a real environment as part of this change.

**Consequence:** MVP-012's hard gate (section 9) is satisfied ahead of MVP-012 itself starting — the vocabulary MVP-012 must respect is now correct in the schema and the domain layer before any write surface is built on top of it, rather than being corrected after the fact.

### MVP-012 update (2026-09-24) — write path and ADMIN-only enforcement landed; moderation workflow remains genuinely unbuilt

Per this record's own hard gate (section 9): MVP-012 (`feature/mvp-012-product-release-editor`)
built the ADMIN-authorized product/release editor, including the
compatibility-evidence write path this section 9 required to wait for it.

**What MVP-012 covers:**
- **Write path** (section 9, "the creator/administrator product editor" —
  collapsed to `ADMIN` under the first-party-only model,
  `docs/final-decisions.md`): `POST /api/admin/products/{id}/compatibility`
  calls `validateCompatibilityEntry` and, on top of it, rejects any
  `evidenceStatus` other than `CREATOR_DECLARED` with a distinct
  `EVIDENCE_STATUS_NOT_PERMITTED_HERE` code — `MARKETPLACE_REVIEWED` is
  refused even for an ADMIN caller, matching "MVP-012's acceptance criteria
  are limited to Creator Declared" exactly as this section already required.
- **Defense in depth at the database boundary**:
  `PrismaCatalogRepository.upsertCompatibilityEntry`
  (`packages/adapters/catalog/src/catalog-repository.ts`) independently
  refuses to persist anything but `CREATOR_DECLARED`, so a future code path
  that skipped the route's own check still cannot reach the database with a
  forbidden status.
- **Authorization (section 6, narrowed)**: the route uses the same
  deny-by-default `requireAdmin()` pattern as every other MVP-012/MVP-017
  route (no session or a non-`ADMIN` role both get an identical 404, role
  re-queried fresh from the database every request). This satisfies "only
  the trusted... workflow, for an authorized [actor], may set" for the one
  actor that now exists (`ADMIN`) — there is no separate creator/moderator
  distinction left to enforce under first-party-only.
- `reviewedAt` is still never accepted from a client request and is
  explicitly nulled by `upsertCompatibilityEntry` on every write it
  performs (consistent with section 4 — only a moderation workflow, which
  does not exist, may ever set it).
- Tests: `apps/web/app/api/admin/products/[id]/compatibility/route.test.ts`
  (rejection of `MARKETPLACE_REVIEWED` and `TESTED`, authorization,
  validator field errors) and
  `packages/adapters/catalog/src/catalog-repository.integration.test.ts`
  (`upsertCompatibilityEntry` defense-in-depth rejection, against a real
  database).

**What remains genuinely unbuilt — still open, no approved successor:**
- The `MARKETPLACE_REVIEWED` transition itself, and everything that would
  perform it: the moderation workflow, `ModerationReview`/`AuditEvent`
  entities, a `moderationReviewId` reference, and the state-transition
  rules of section 3 beyond "create → Creator Declared" (which MVP-012
  effectively provides simply by never offering anything else). MVP-013,
  which was going to own this, is Superseded under the first-party-only
  model (`docs/final-decisions.md`) with no approved successor story.
- The legacy-row inspection query (section 5) — still not run; still no
  rows to inspect.
- Public display of a reviewed date, and the "material change" definition
  (section 3) — both remain undecided, and moot while nothing can ever
  reach `MARKETPLACE_REVIEWED`.

**Consequence:** TD-008 stays **Partially Resolved**, not Resolved. The
schema/validator/presentation correction (2026-09-24) plus the write path
and authorization enforcement (2026-09-24, MVP-012) are both done; the
moderation-workflow half of this record has no owner until a new story is
approved to replace superseded MVP-013.
