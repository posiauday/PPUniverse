## What was deferred and why
BUG-040 made sign-in return readers to the page that asked them to sign in. The password sign-up path wasn't changed. Sign-up sends a confirmation email, and the link in it (`/password/confirm?token=…`, built in `apps/web/lib/password-auth.ts`) doesn't carry where the reader started, so after confirming they land on `SIGNED_IN_PATH`.

Fixing it means storing the return path with the confirmation token (or adding a checked `next` to the link), accepting it in `POST /api/auth/password/signup` and using it in `ConfirmSignUpForm`. That's a change to the token flow and its email, so it was kept out of the same-day fix.

## What's left
1. Carry a checked same-site return path from `/signin` → `/signup` → the confirmation link → `/password/confirm`.
2. Use `continuePath()`'s rule to check it at each step.
3. Test: sign up from a component's Copy YAML and land back on the component after confirming.
