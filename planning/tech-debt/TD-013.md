## What was deferred and why
BUG-013 found that on `/account/sessions`, calling `router.refresh()` (in
`SessionRevokeButton`, after a successful revoke) can, in Firefox, leave the `<title>`
element removed from `<head>` entirely for a brief window while the page re-renders with
fresh data — not merely emptied. The approved fix (2026-09-21, "Product-owner decision —
BUG-013 and signin-sent") is a **mitigation, not a root fix**: `SessionsHeading` now
closes that window itself, by creating or correcting the `<title>` element on every
re-render it sees. It does not explain, and does not fix, why the framework removes the
element during the transition — that gap is between `router.refresh()` starting a
same-route data refresh and the framework re-applying the route's declared document
metadata once the refresh completes.

`SessionRevokeButton` is the only call to `router.refresh()` in the application today
(verified: `grep -rn "router.refresh" apps/web/app`). **Any future route that calls
`router.refresh()` is not covered by this mitigation** and may exhibit the same gap;
nothing currently guards against that beyond this one page's specific fix.

The underlying mechanism was not investigated (out of scope for a minimal, one-file
mitigation): whether this is a documented Next.js App Router behavior around metadata
streaming and Suspense-boundary re-suspension during a same-route refresh, or something
narrower. It also could not be reproduced deterministically locally — delaying the RSC
refetch response (0/300/800/1500ms) and running concurrent revoke cycles under load
across all three engines never reproduced it; it has only ever been observed in CI,
Firefox, twice in five runs.

## Risk if left unresolved
- A future story that calls `router.refresh()` on a different route inherits the same
  risk, with nothing to catch it until it happens to show up in CI (or not, given how
  narrow and hard to reproduce the window is) and gets its own bug report.
- The mitigation's own regression coverage is a unit test of its decision logic only
  (`SessionsHeading.test.ts`), not a reproduction of the race; if the framework's
  behavior changes (a Next.js upgrade), nothing would signal whether the underlying gap
  got wider, narrower, or moved to a different observable symptom.

## Proposed resolution
When another story needs `router.refresh()` on a route with document-metadata
requirements, check whether the same gap applies (repeat the reproduction attempts
above, ideally on the actual Next.js version in use at the time) before assuming the
`/account/sessions` mitigation's pattern is unnecessary elsewhere. If the underlying
framework behavior is ever understood well enough to fix generally (for example, a
shared hook, or an upstream Next.js fix), replace the per-page mitigation with it and
close this record.
