## What was deferred and why

`apps/web/app/admin/audit/page.tsx` reads the `ENTRY_LIMIT` (100) most
recent rows from each of three source event tables (`ProductStatusEvent`,
`DeletionRequestEvent`, `ArticlePublishEvent`), merges and sorts them, then
truncates to 100 overall. There is no "next page" link, no date-range
filter, and no per-domain filter. This mirrors TD-014's identical, already-
accepted precedent (`/admin/deletion-requests` has no pagination either) --
a deliberate scope narrowing for a low-volume admin surface, not a defect
at current or near-term scale.

## Risk if left unresolved

Once the combined event volume across all three domains exceeds 100 rows
between admin visits, older events silently fall off the bottom of the
list with no way to reach them from this page (a fresh Postgres query
against the source tables directly would still find them). At current
scale (a handful of sensitive admin actions per day, if that), this is not
a practical problem.

## Proposed resolution

Not scheduled. A future pass would add cursor-based pagination (matching
this codebase's established `DEFAULT_PAGE_SIZE`/`MAX_PAGE_SIZE` convention
from `@ppu/domain-catalog`'s search-params handling) and likely a
domain/date filter, once real usage shows the 100-row window is
insufficient.
