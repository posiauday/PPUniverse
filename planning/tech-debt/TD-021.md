## What was deferred and why

Explicitly out of scope by direct product-owner instruction ("PRODUCT-OWNER
DECISION AND IMPLEMENTATION AUTHORIZATION -- MVP-014 -- IMMUTABLE PUBLISHED
RELEASES", section on scope boundaries): "no compatibility/licence
snapshots." MVP-014 makes the `Release` row and its attached `ReleaseFile`s
immutable once published -- `publishedAt` is set exactly once, enforced by
an atomic conditional database update, and no application code path can
attach, detach, or replace a file on an already-published release. It does
**not** snapshot the `Product`'s licenses (`ProductLicense`), support policy
(`SupportPolicy`), or compatibility entries (`CompatibilityEntry`) at the
moment a given release is published. Those rows remain product-scoped and
mutable, per the existing MVP-005/MVP-012 model, and were correctly left
unchanged -- MVP-014's authorization was explicit that the product-scoped
`Entitlement` model and evidence tables stay as-is.

## Risk if left unresolved

A visitor viewing an older, already-published release has no way to see
what license terms, support commitment, or compatibility claims were true
*at the time that release was published* -- only what is true of the
`Product` right now. If an administrator edits a license, tightens a
compatibility claim, or changes the support policy after release `1.0.0`
was published and before release `1.1.0` is published, the public product
page's evidence display silently applies to every previously-published
release retroactively, even though the underlying files for `1.0.0` never
changed. This is a customer-trust and audit gap (a purchaser of `1.0.0`
under one set of licence terms has no record of what those terms said at
purchase time), not a data-integrity defect -- the `Release`/`ReleaseFile`
immutability guarantee itself holds regardless.

## Proposed resolution

Not scheduled, not designed. A future story would need to decide: whether
to snapshot license/compatibility/support evidence per-release at publish
time (new join tables or a denormalized JSON snapshot column), how to
display historical evidence for a non-current release, and how this
interacts with the existing product-level evidence display MVP-005 built
(which has no per-release concept today). No schema, validator, or
production code is changed by recording this gap.
