## What was deferred and why
The "local Postgres without Docker" workflow (session memory
`local-postgres-without-docker.md`) starts `embedded-postgres` from a small
Node script in the session scratchpad (outside the tracked repository —
`packages/db/scripts/` has no such start script; only the tracked
`provision-test-schemas.mjs`, which assumes a database is already running).
That start script's only cleanup path is a `SIGTERM` handler calling
`pg.stop()`.

On Windows, `embedded-postgres` launches `postgres.exe` via `pg_ctl` as its
own independent console process, not a child that necessarily dies with its
Node parent's process group. If the Node wrapper's process is torn down
without `SIGTERM` reaching it specifically (observed during this session:
an agent's background task ending without an explicit graceful-shutdown
step), `pg.stop()` never runs and `postgres.exe` survives orphaned, holding
its listening port and shared-memory segment. This was found and reproduced
directly in this session: 9 orphaned `postgres.exe` processes from earlier
runs, confirmed via `tasklist`, causing a fresh instance on the same
data-directory path to fail with `initdb: error: directory ... exists but
is not empty` and, after clearing the directory, `FATAL: pre-existing
shared memory block is still in use` until a different port/data-directory
was used instead.

This is a tooling-hygiene gap in session/agent workflow, not a defect in any
tracked repository file — no `packages/db/scripts/*.mjs` file needed to
change, and none was.

## Risk if left unresolved
Repeated DB-gated local test/verification passes accumulate orphaned
`postgres.exe` processes over a long session, eventually exhausting a
predictable port or causing confusing `initdb`/shared-memory failures for
the next person (or agent) who tries to reuse the same data-directory path,
without anything in the repository itself being at fault.

## Proposed resolution
Not a repository code change. Recommended workflow correction (to fold into
the `local-postgres-without-docker` memory note, not into `packages/db/`):
- Record the exact spawned `postgres.exe` PID (or the embedded-postgres
  data-directory path) at start time.
- Always invoke the script's `SIGTERM` path explicitly at the end of a
  verification pass (not just registering the handler and hoping the
  process is torn down cleanly) -- e.g. a paired `stop-*.mjs` that connects
  and calls `pg.stop()` directly, invoked in a `finally`-equivalent step.
- Before starting a new instance on a previously-used data-directory/port,
  check for and report any already-listening process on that port rather
  than assuming a clean slate.
- Never broadly kill unrelated `postgres.exe`/`node.exe` processes to work
  around this -- only ever stop the specific instance a script itself
  started, using its own recorded identity.
