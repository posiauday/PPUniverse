## What was deferred and why
MVP-002 provisioned a temporary Supabase project (`ppuniverse-dev`, `cjktrbgrvstsbbuncqzu`) to verify the Identity schema migration and constraints against a real PostgreSQL instance. Supabase's own security advisor (`get_advisors`) flagged: RLS disabled on all tables (`users`, `accounts`, `sessions`, `verification_tokens`, and as of MVP-006, `file_scans`) — `ERROR` level, since these tables are exposed to Supabase's PostgREST layer for the `anon`/`authenticated` roles by default. The remediation SQL was intentionally **not** auto-applied (enabling RLS with no policies would block all access, including our own Prisma connection's queries through the pooler if it ever went through PostgREST — it currently doesn't, since the app connects via a direct Postgres connection string, not Supabase's client libraries or anon key).

## Risk if left unresolved
Low *for this specific temporary dev project* as currently used (direct Postgres connection only, anon/publishable key never embedded anywhere in the app). Becomes real risk if: (a) this project is ever promoted beyond throwaway dev/test use, or (b) anyone adds Supabase client-library access (`supabase-js`) using the anon key without first enabling RLS — at that point every row in these tables is readable/writable by anyone holding the anon key.

## Proposed resolution
`docs/final-decisions.md` (2026-09-17 product-owner constitution) resolved `docs/open-questions.md` item 16 directly: RLS is approved and required. Implemented as RLS-enabled-with-zero-policies on every table — standard PostgreSQL DDL (`ALTER TABLE ... ENABLE ROW LEVEL SECURITY`), no Supabase-specific `auth.uid()`/PostgREST dependency, so it's portable regardless of the still-open hosting decision (open question 5). Zero policies is correct and sufficient because the app never grants the `anon`/`authenticated` roles any legitimate access at all (it only ever connects as the table-owning role via Prisma) — Postgres's default-deny-when-RLS-enabled-with-no-policies behavior is exactly the desired outcome.

## Resolved by (story/commit, once closed)
`packages/db/prisma/migrations/20260917020000_enable_row_level_security/`. Verified against the `ppuniverse-dev` Supabase project (2026-09-17): applied via `apply_migration`; confirmed the table-owning role's own INSERT/SELECT/DELETE queries are unaffected (bypasses RLS as owner, exactly as designed); re-ran `get_advisors` and the `rls_disabled` **ERROR**-level finding is gone, replaced by an expected, much-lower-severity `rls_enabled_no_policy` **INFO**-level note (Supabase's linter correctly observing that RLS is on with no policies — the deliberate design, not a gap). Migration not yet applied outside this verification project — applies automatically via `prisma migrate deploy` (CI, or any environment) the next time it runs, since it's a normal versioned Prisma migration.
