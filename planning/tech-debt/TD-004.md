## What was deferred and why
The TRD's architecture default is a durable queue for scans, webhooks, email, indexing, and media processing (`CLAUDE.md` "Suggested implementation baseline"). `apps/web/lib/complete-file-upload.ts`'s `completeFileUpload()` runs the entire MVP-006 pipeline (re-check upload policy against actual size, magic-byte verification, malware scan, zone move) synchronously inside the `POST /api/files/uploads/complete` request handler. No story yet owns setting up the actual job queue (BullMQ is named in the TRD baseline but `apps/worker` is still just a boot-proving scaffold from MVP-001 — no consumers exist).

## Risk if left unresolved
A large file (up to the 50MB policy limit) held in memory (`getObject` reads the full object) and scanned inline blocks the HTTP request/response cycle for however long ClamAV's `INSTREAM` scan takes — this does not scale under concurrent uploads and risks request timeouts on slow scans. It also means a crash mid-scan leaves a `FileScan` row stuck in `SCANNING` with no retry mechanism.

## Proposed resolution
Move the pipeline into a real queue consumer once a story establishes the job-queue infrastructure (the TRD names this as a cross-cutting foundation, not owned by any single current MVP-006-adjacent story — worth an explicit backlog decision on which story picks it up, e.g., a dedicated "Job queue foundation" story or folded into whichever of MVP-009/MVP-012/MVP-019 needs durable background work first). The `POST /api/files/uploads/complete` endpoint would then enqueue and return `202`/`QUARANTINED` immediately, with the client polling `GET /api/files/{id}` (already returns scan status) for the terminal result.
