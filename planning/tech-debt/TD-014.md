## What was deferred and why
`PrismaPrivacyRepository.listActiveDeletionRequests()` and the `/admin/deletion-requests`
page it backs return every request in an active state (`SUBMITTED`, `UNDER_REVIEW`,
`APPROVED`) across the entire product, in one unbounded query, ordered oldest first.
There is no page size limit, no filter (by state, by date range, by requester), and no
alternate sort. This was a deliberate scope narrowing to ship the story within its
authorized boundary (consent capture, deletion requests, and the admin surface needed to
see/action them) — building real admin tooling (pagination, search, filtering) was not
part of that scope and no decision authorized it.

At current and near-term marketplace scale (no production inventory or user base yet —
confirmed by the pre-work analysis), this is not a functional defect: the query returns
an empty or very small result set. It becomes a real problem once the volume of active
deletion requests grows large enough that the page becomes slow to render or difficult
for an admin to scan.

## Risk if left unresolved
- A future admin visiting the page once real request volume exists sees every active
  request in one long, unpaginated list, with no way to narrow it to what they are
  currently working on.
- The underlying query has no `take`/`skip`, so response time scales linearly with the
  total number of active requests system-wide, not with what is actually displayed.

## Proposed resolution
When admin tooling for this surface is prioritized: add pagination (a `take`/`skip` or
cursor-based page in `PrismaPrivacyRepository.listActiveDeletionRequests()`), a state
filter, and a sort option (oldest/newest first). No schema change is needed — the
`DeletionRequestEvent.occurredAt` index already supports ordering; only the repository
method and the page's query parameters need to change.
