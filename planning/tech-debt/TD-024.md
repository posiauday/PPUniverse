## What was deferred and why
Site search covers published guides since the board fidelity pass (`docs/final-decisions.md`, "Board fidelity pass"; open question 63). To land it inside MVP-031:
- `PrismaContentRepository.searchPublishedArticles` (`packages/adapters/content/src/content-repository.ts`) builds the weighted `tsvector` (title, excerpt, body) for every published article on every query. No generated column and no GIN index exist, so no migration was needed.
- `/search` lists the best 20 guide matches (`GUIDE_RESULT_LIMIT` in `apps/web/app/search/page.tsx`), on the first page only. Components keep their own paging.

At launch the library holds about 24 guides, so a per-query scan is cheap, and 20 results is more than any query returns.

## Risk if left unresolved
- Search time grows with the total size of every article body. With hundreds of long guides, each search reads and parses all of them.
- A query matching more than 20 guides silently shows only the best 20, with no way to see the rest.

## Proposed resolution
- Add a stored generated `tsvector` column on `articles` (same weights) with a GIN index, in a reversible migration, and query it.
- Page the guide results (or add a "more guides" link to a guides-only results view), using the same `noindex, follow` rule as today.

## Trigger to revisit
The library passes 150 published guides, search latency shows in telemetry (`catalog.search` logs `guideCount`), or a common query returns 20 guides.
