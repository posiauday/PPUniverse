## What was deferred and why
`PrismaNotificationService.sendTransactional`/`sendOptional`
(`packages/adapters/notifications`) call the configured `EmailAdapter` (Resend, or
`ConsoleEmailAdapter` when no vendor key is configured) directly inside the HTTP
request that triggers it — `apps/web/lib/auth.ts`'s sign-in link, and
`POST /api/account/deletion-requests`'s acknowledgement. This is the same class of
gap [TD-004](TD-004.md) already names for MVP-006's file-scan pipeline: the TRD's
architecture default is a durable queue for email (`CLAUDE.md`, "Suggested
implementation baseline"), but `apps/worker` remains the MVP-001 boot-proving
scaffold with no consumers, and no story yet owns setting one up. Building a queue
was explicitly out of scope for MVP-018's own authorization
(`docs/final-decisions.md`, "MVP-018 open question 49": "do not build a queue").

There is also no retry: a failed send is recorded (`EmailSend`, status `FAILED`) and
surfaced via telemetry, but never attempted again. For the sign-in link, the failure
propagates to the caller (`next-auth`'s own existing error-page behaviour, unchanged
by this story). For the deletion-request acknowledgement, the failure is deliberately
swallowed at the route's own call site — the record is authoritative, the email is a
courtesy (question 49, constraint 3) — so a transient provider outage silently means
the user never receives that one email, with no automatic follow-up.

## Risk if left unresolved
- A slow or unresponsive vendor call blocks the HTTP request/response cycle for
  however long it takes (or times out), the same request-latency risk TD-004 already
  documents for file scanning.
- A transient failure (not just a provider outage — a momentary network blip) has no
  path to succeed later; the recipient simply never gets that message, with only the
  `EmailSend` audit row and a telemetry event as evidence it happened.
- Every future transactional message this project adds inherits the same
  synchronous-with-no-retry shape unless a shared queue exists by then.

## Proposed resolution
When a story establishes real job-queue infrastructure (the same open item TD-004
names — a dedicated "job queue foundation" story, or folded into whichever future
story needs durable background work first), move `PrismaNotificationService`'s calls
into a queue consumer: the triggering route enqueues a job and returns immediately
(matching TD-004's own proposed shape — `202`, with `EmailSend`'s status polled or
pushed rather than known synchronously), and the consumer can safely retry a
transient failure with the `EmailSend` audit trail itself as the de-duplication
record (a `messageType` + `userId` + a bounded time window is enough to detect and
skip a duplicate attempt).

## Decision (2026-09-24, direct product-owner instruction — `docs/final-decisions.md`, "TD-004 architecture and sequencing")

Full pre-work: `planning/prework/TD-004-prework-analysis.md`.

- **Architecture decided** (shared with TD-004): a Postgres-backed job queue. A foundation story is proposed (`PROP-007`, `planning/proposed-stories.md`), not approved, not scheduled, blocked on BUG-015.
- **Sign-in email semantics resolved, and explicitly NOT changed by the eventual migration:** the sign-in link send is **not migrated** onto the queue. Its current blocking-and-failing behavior is deliberate and correct for a magic-link flow — a user who cannot receive the link has not signed in. **Only the deletion-request acknowledgement email migrates**, once the foundation exists.
- **Retry policy decided as a starting default, revisable:** 3 attempts, exponential backoff from 30s, then dead-letter — applied uniformly until real failure-rate data justifies per-type tuning (`docs/open-questions.md` item 54).
- Same BUG-015-first sequencing as TD-004 (`docs/final-decisions.md`, section 3): this story's own migration cannot land before the foundation exists, and the foundation cannot land before BUG-015 is resolved.
