## Summary
The catalog search helpers assume every query-string value is a single string. Next.js passes a repeated parameter as an array, and `normalizeQuery` calls `.trim()` on it, which throws. `/search?q=a&q=b` and `/categories/<slug>?q=a&q=b` return HTTP 500 instead of degrading to a safe default. `packages/domain/catalog/src/search-params.ts` documents the opposite intent ("Never throws on bad input").

Found while verifying MVP-021's category canonical policy against real pages. **Not fixed here:** the MVP-021 authorization forbids modifying MVP-004's filtering or search functionality.

A malformed URL fails; ordinary searches work. No data is exposed. Each such request logs an error, which is noise for error monitoring.

## Environment
- Environment: local (Next.js dev server, real local Postgres with test rows), 2026-09-21

## Steps to reproduce
1. Request `/search?q=a&q=b`.
2. Request `/categories/power-apps-components?q=a&q=b`.

## Expected behavior
The page renders, using a safe default for the malformed value (the documented behavior of `search-params.ts`).

## Actual behavior
HTTP 500 for both. Control requests on the same server: `?q=a` → 200; `?page=1&page=2` → 200; `?sort=recent&sort=alphabetical` → 200 (only `q` is affected, because it is the only one that calls a string method).

## Evidence
Server log:
```
TypeError: raw?.trim is not a function
    at normalizeQuery (packages/domain/catalog/src/search-params.ts:27:24)
    at CategoryPage (app/categories/[slug]/page.tsx:57:31)
    at SearchPage (app/search/page.tsx:31:31)
```
`git diff develop` shows this branch does not touch `apps/web/app/search/page.tsx`, `packages/domain/catalog/src/search-params.ts`, or the `normalizeQuery` call in the category page.

## Security or privacy impact
- [ ] None identified. It is a robustness defect on public read-only pages.

## Accessibility impact
- [ ] None.

## Suggested fix
Make `normalizeQuery` (and the two call sites' types) accept `string | string[] | undefined` and fall back to the first value or to "no query", with a unit test for the repeated-parameter case. This changes MVP-004 search behavior, so it needs a small corrective story or an explicit product-owner approval.
