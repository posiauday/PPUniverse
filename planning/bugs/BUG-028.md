## Summary
After PR #90 (votes and reports) was merged, `develop`'s accessibility shard 3 failed: the WebKit keyboard check for the `learn-voted` state at 1280 px reported every control above the feedback block as "no keyboard route reached". The same check had passed on #90's own branch with the same code. PR #91 then failed the same way.

## Cause
After "Yes, fixed", `GuideFeedback.tsx` shows the thanks and moves focus to it with `requestAnimationFrame`. The thanks paragraph is hidden while it is empty (`empty:hidden`), and that frame could run **before** React had rendered the thanks text. Focus then went nowhere: a keyboard or screen-reader user was dropped at the top of the page instead of hearing the thanks.

The gate exposed it two ways:
- on CI, focus sometimes moved late, in the middle of the keyboard walk, so the walk restarted from the thanks and missed everything above it;
- locally, after the gate state was changed to wait for the thanks to have focus, Firefox and WebKit showed it often never got focus at all (11 of 21 checks failed in one local run).

The "Not yet" path and "Something here changed?" moved focus to the note box the same way.

## Fix
- `GuideFeedback.tsx`: focus moves in an effect, after React has rendered (`focusNext` state), for the thanks and for the note box.
- The `learn-voted` gate state now waits until the thanks **has focus**, which checks the behaviour we promise.
- Checked locally: every vote and report state passes in Chromium, Firefox and WebKit at all widths, light and dark.

## Expected behavior
After a vote, focus lands on the thanks (Yes) or the note box (Not yet), in every browser.
