Follows `planning/github/04-bug-template.md`, as BUG-028 did.

## Summary
Every table has row-level security (RLS) on with no policies (`docs/final-decisions.md`, "RLS implementation note"). Four tables added this week were created without it: `library_components` and `component_events` (migration `20261015000000_add_component_library`), and `site_switches` and `site_switch_events` (`20261016000000_add_site_switches_and_coming_soon`).

## Severity
P0 by the template's definition (security). No exposure is known. Reaching these tables needs the Supabase project's anon key, which the site never publishes, because the app talks to Postgres only through Prisma. But with that key, Supabase's PostgREST API would allow:
- reading every component's YAML, including the ones that need sign-in;
- changing components;
- flipping the site switches.

## Environment
Production and every database where those two migrations ran. Found by the agent while adding MVP-050's tables, by checking each migration for `ENABLE ROW LEVEL SECURITY`.

## Cause
Both migrations were generated with `prisma migrate diff`, which never adds RLS, and the RLS line was not added by hand. Nothing checked for it.

## Fix
- Migration `20261016000100_enable_rls_component_and_switch_tables` turns RLS on for the four tables. The app connects as the tables' owner, which bypasses RLS, so nothing in the app changes. On a table that already has it, it does nothing.
- `packages/db/src/row-level-security.test.ts` reads every migration and fails CI for any table created, and not later dropped, without `ENABLE ROW LEVEL SECURITY`. Without the fix it names exactly these four tables.

## Expected behavior
Every table has RLS on from the migration that creates it.

## For the product owner
After the next release, Supabase's Security Advisor should show no "RLS disabled in public" warnings.
