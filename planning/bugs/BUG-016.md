Follows `planning/github/04-bug-template.md`.

## Summary
At the end of a Playwright worker, fixture cleanup (`packages/e2e/src/seed.ts`) deletes the worker's fixture users. `EmailSend.userId` is a Restrict FK (MVP-018, deliberately, as an audit trail), and cleanup never deleted `EmailSend` rows. When a test left one behind for a fixture user, the user delete failed with `email_sends_userId_fkey` and the whole worker failed.

## Severity
- [x] P3 — minor. It affects the test harness only: an intermittent red CI run and leftover test rows. No user impact and no data exposure.

## Affected requirement / feature
- NFR-001 (the accessibility gate, MVP-023). The gap was introduced by MVP-018 (EmailSend), whose story updated no cleanup code.

## Environment
- CI, GitHub Actions Linux runner, **WebKit** worker. Run `36664530308` (PR #31, accessibility shard 4/4), 2026-09-30.

## Steps to reproduce
Reproduced locally and deterministically: `pnpm --filter @ppu/e2e exec playwright test tests/a11y/pages.spec.ts --project=webkit -g "privacy-loading" --workers=1`, which fails cleanup on `deletion_requests_userId_fkey`.

**Root cause (proven).** Three states use `interceptAndHold` to freeze a POST so a "submitting" UI state can be scanned: `privacy-loading` (deletion request), `unsubscribe-loading` and `privacy-consent-loading`. The helper never resolved the route, assuming Playwright discards open routes with the page. **WebKit instead delivers the still-pending request to the server when the page closes.** The real route then ran during worker teardown. It created a deletion request, and an EmailSend row through the confirmation email, **after** cleanup had already deleted those tables, so the user delete failed.

## Expected behavior
Cleanup removes every row that references the fixture users, whatever created it, before deleting the users.

## Actual behavior
`AggregateError: Cleanup of zz-e2e-a11y-ef8f73-w0- rows failed`, caused by `PrismaClientKnownRequestError`: foreign key constraint `email_sends_userId_fkey` on `prisma.user.deleteMany()`.

## Evidence
- The failing run is above.
- The very next run, on the stacked branch with the same code (`36664544830`, PR #32), passed every check. So the failure is intermittent, not deterministic.
- The MVP-027 dark-theme pass runs every page state once more, `privacy-loading` included, which made the rare path likelier to occur.

## Security or privacy impact
- [x] None. Test harness only; all fixture addresses are reserved `example.invalid` addresses, and the email adapter in tests is the console adapter.

## Accessibility impact
- [x] None. Every page check in the failing run passed; only the cleanup step failed.

## Resolution (2026-09-30, MVP-027 slice 1)
1. **The fix: held requests are aborted, never left pending.**
   - `interceptAndHold` moved to `packages/e2e/src/held-requests.ts`, which remembers each held route.
   - A new auto fixture, `heldRequests` in `fixtures.ts`, calls `abortHeldRequests(page)` after every test, before the page closes.
   - Nothing held can reach the server any more.
2. **Completeness:** cleanup also deletes `EmailSend` rows for the fixture users, beside the consent and deletion-request rows it already cleared for the same Restrict-FK reason.
3. **Verified:**
   - The deterministic reproduction now passes: 15/15 over 3 repeats.
   - Every privacy, unsubscribe, consent and fixture-cleanup state on WebKit and Chromium (4 workers): 186/186, with no cleanup failures.
   - A 40-worker local run showed only WebKit-on-Windows browser-process crashes under that load, which is a local-environment limit, and no foreign-key failures.
