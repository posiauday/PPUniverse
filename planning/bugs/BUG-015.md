Follows `planning/github/04-bug-template.md`. Found while verifying CI on
`chore/accessibility-suite-sharding` (PR #12) — a CI-only, docs-only change with no
product or test-logic modifications, so this defect is confirmed pre-existing, not
introduced by that PR.

## Summary
`packages/adapters/catalog/src/catalog-repository.integration.test.ts`'s
`listSitemapEntries (MVP-021) > returns the same order on every call` test calls
`repo.listSitemapEntries(50_000)` twice in immediate succession and asserts the second
call's `productSlugs` deeply equals the first's. `listSitemapEntries` (`catalog-repository.ts:105`)
queries `this.db.product.findMany({ where: { status: "PUBLISHED" }, ... })` — unscoped
by any test-run or worker prefix, by design: it is a real sitemap query and must see
every published product, not just ones a given test created. In CI, `@ppu/adapter-catalog`
and `@ppu/adapter-entitlements` are separate pnpm packages whose `test` tasks Turborepo
can run **concurrently** (no dependency edge forces them to run sequentially), and both
connect to the **same** `DATABASE_URL` Postgres service container with no schema or
transaction isolation between packages. When `@ppu/adapter-entitlements`' own integration
suite inserts its `entitlement-repo-product` fixture (a `PUBLISHED` product, by that
package's own test data) in the window between the catalog test's two calls, the second
call's `productSlugs` gains that extra slug and the equality assertion fails.

## Occurrence

| Run | Commit | Result |
|---|---|---|
| CI run `35832890876`, job `107089396490` | `cd8ecce` (docs-only push, unrelated to this defect) | `FAIL src/catalog-repository.integration.test.ts > ... > returns the same order on every call` — `AssertionError: expected [...7 slugs] to deeply equal [...6 slugs]`; diff shows the received array has one extra entry, `"entitlement-repo-product"`, not present in the expected (first-call) array |
| Same PR, job re-run (`gh run rerun --job`) | Same commit `cd8ecce` | **Passed** — `Format, lint, typecheck, test, build` green, 2m46s |

**Confirmed flaky, not deterministic**, by direct re-run rather than assumed: the exact
same commit, re-run without any code change, passed cleanly on the retry. This is
consistent with the race-condition explanation above (the two packages' test tasks
happening not to overlap that specific window on the second attempt).

## Severity
- [x] P3 — minor: it is a test-suite isolation gap, not a production defect.
  `listSitemapEntries`'s production behavior (an unscoped scan of all `PUBLISHED`
  products) is correct and required for a real sitemap; nothing about a real deployment
  runs two different packages' test fixtures against the same live database
  concurrently. The practical impact is confined to intermittently, spuriously failing
  the required `Format, lint, typecheck, test, build` CI check, which could block an
  unrelated PR's merge and force a re-run to confirm it was a flake rather than a real
  regression (as happened here).

## Affected requirement / feature
- FR-017 (sitemap). Delivered by MVP-021 (`packages/adapters/catalog/src/catalog-repository.ts`).
  The defect is in the **test suite's isolation**, not in FR-017's delivered behavior.

## Environment
CI (`ubuntu-latest`), the `build-and-test` job's shared Postgres service container
(`postgres:17-alpine`, one container per job run, shared by every package's `test`
task in that job). Not reproduced locally in this investigation; plausible locally too
under `pnpm test` at the repo root if Turborepo's default concurrency happens to
overlap the two packages' relevant windows, but this was not attempted here since the
CI evidence above already confirms both the failure and its flakiness directly.

## Steps to reproduce
Not reliably reproducible on demand — depends on Turborepo's task scheduling causing
`@ppu/adapter-catalog`'s and `@ppu/adapter-entitlements`' `test` tasks to overlap such
that the entitlements suite's `entitlement-repo-product` insert lands inside the
catalog suite's two-call window. Occurred once in the CI runs observed so far.

## Expected behavior
`listSitemapEntries (MVP-021) > returns the same order on every call` passes
regardless of what other packages' integration suites are doing concurrently in the
same job.

## Actual behavior
The test can observe a different, larger `productSlugs` array on its second call than
its first, because another package's concurrently-running integration suite inserted a
`PUBLISHED` product into the same shared database in between the two calls.

## Evidence
- Raw CI log, run `35832890876`, job `107089396490`: `AssertionError: expected
  [ 'catalog-repo-detail-full', …(7) ] to deeply equal [ 'catalog-repo-detail-full',
  …(6) ]`, diff showing `+ "entitlement-repo-product"` as the sole addition.
- Same commit, same job, re-run: passed (`36 passed`, this test included, per the
  `Test Files 1 passed` / no `FAIL` line on the re-run).

## Options, not yet decided
Recorded for a future maintainer/product-owner decision, not acted on here (out of
scope for the CI-infrastructure PR this was found during):
1. Scope `listSitemapEntries`'s test assertions to slugs the test itself created
   (filter both calls' results to a known test-prefix before comparing), leaving the
   production query itself untouched.
2. Force `@ppu/adapter-catalog` and `@ppu/adapter-entitlements` (and potentially other
   integration-test packages sharing one Postgres container) to run sequentially in
   Turborepo's task graph, trading some CI time for full cross-package isolation.
3. Give each package's integration-test run its own database/schema in CI (a larger
   infrastructure change, closer to the isolation per-worker fixtures already use
   within a single package).
None of these is approved; no product or test code should change under this record
without that decision, per this project's standing rule against unauthorized fixes to
already-delivered work found in passing.

**Independent recommendation received (2026-09-23), NOT an approved decision.** GitHub
Copilot, asked for an opinion while reviewing the unrelated PR #12 this bug was found
during, recommended option 3 (per-package database isolation) over options 1 and 2:
sequencing the two packages' test tasks (option 2) "buys correctness with permanent
serialisation, and silently returns the moment a third package touches the same
tables"; test-side scoping (option 1) is "correct" in principle but "a convention every
future author must remember," and weakening `listSitemapEntries`'s own test to dodge
the race would make it less faithful to the unscoped-scan behavior it's meant to
verify. Per-package isolation "removes the shared mutable state rather than
coordinating around it," matching the pattern the accessibility suite's own sharding
already uses (one Postgres service container per shard) and the reserved-prefix
convention already used for accessibility test data. Caveat raised: any per-package
database provisioning must apply the same migrations as the shared one, including
`ENABLE ROW LEVEL SECURITY`, or the tests would run against a schema that doesn't
match production. **This is recorded as input for whoever makes this decision, not
adopted as one** — per this project's Decision Validation Rule, a reviewer's
recommendation (AI or otherwise) is not itself an approved source; it becomes one only
if a product owner or maintainer explicitly decides on it. Status stays Open.
