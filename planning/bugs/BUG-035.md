## Summary
Three accessibility gate runs failed in WebKit with "the page has no keyboard stops", each on a different page a signed-in member is denied: `admin-updates-denied` at 1280 px (#125), then `admin-products-denied` and `admin-components-denied` at 320 px (#126). Each is the site's 404 page. Each passed on the next run, and a local WebKit run passed 24 of 24.

## Cause (likely; not reproduced locally)
The 404 states had no `prepare` step, so the keyboard walk began as soon as the page loaded, possibly before the 404 page had hydrated. The walk stops when focus lands on the page body. If hydration replaces the control the first Tab has just focused, focus falls back to the body and the walk ends with no stops. WebKit is the most exposed, because its Tab key skips links, so a 404 page has only a few stops to lose.

## Fix
Every gate state that expects a 404 (21 states) now waits until the "Page not found" heading has hydrated (`notFoundSettled` in `packages/e2e/src/pages.ts`). This also checks that each of them really shows the 404 page.

Checked locally: all 21 states pass the page matrix in Chromium and the keyboard walk in WebKit at 320 px.

## Expected behavior
The gate checks each state after the page has settled, as BUG-028 and BUG-031 established for error states.

## Accessibility impact
- [x] None for readers. Only the check's timing changed.
