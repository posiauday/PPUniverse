## Summary
On 2026-10-07 at about 07:20 UTC, every page of lowcodestacks.com that reads the database returned HTTP 500: the home page, `/learn` and `/sitemap.xml`. Static pages such as `/how-we-write` still worked. The site recovered by itself at about 07:31 UTC.

Supabase's pooler (Supavisor, transaction mode) logged `(EMAXCONN) max client connections reached, limit: 200`. Between 07:20 and 07:25 it logged 275 new client connections and only 2 closed ones. In every earlier hour that day, opens and closes were roughly equal, with no EMAXCONN errors.

## Cause
`@ppu/db` built its `pg` pool with the library defaults: up to 10 connections per pool, idle ones closed after 10 seconds. On Netlify every function instance has its own pool. A burst of requests starts many instances, each opening several connections for a page's parallel queries. A frozen instance runs no timers, so its idle connections stay open until Netlify discards the instance. About 20 to 30 instances were therefore enough to fill the 200 client connections.

BUG-012 was a different fault: a new pool for every query. That fix (one cached client per instance) still holds.

## Steps to reproduce
Send many concurrent requests to database-backed pages on the production site, enough to start 20 or more function instances. Not reproduced on purpose: the evidence is the pooler log above.

## Expected behavior
A burst of traffic slows pages down but does not exhaust the pooler.

## Fix
- `packages/db/src/index.ts`: the pool now has `max: 3` and `idleTimeoutMillis: 5_000`. That allows about 65 concurrent instances under the 200 limit, and a page's few parallel queries still run in parallel.
- `packages/db/src/client-adapter.test.ts` asserts the pool settings.
- What caused the burst is unknown, because Netlify's function logs aren't available to us here. Search Console was verified the day before, so a crawler is a likely source.
- If bursts grow past about 65 instances, the next step is the Supabase plan's pooler limit, a product-owner decision.
