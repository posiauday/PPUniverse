Follows `planning/github/04-bug-template.md`. Found in the full-site code review the product owner asked for on 2026-10-10.

## Summary
normalizeQuery had no length limit, so a query of several kilobytes went into full-text search and highlighting over every guide on an uncached page. parsePage accepted 1e20 or 1e300, which became an out-of-range SQL OFFSET, so /search and category pages failed (500).

## Cause
Only the page size was capped.

## Fix
A search term is cut at 200 characters and the page number at 1,000; anything not a safe whole number is page 1.

## Steps to reproduce
Open /search?q=<8 KB of words>, or /search?page=1e300.

## Expected behavior
Normal results, or an empty last page.

## Actual behavior
Heavy database work for the long query; an error page for the huge page number.

## Security or privacy impact
A cheap way to load the database and to make pages fail.
