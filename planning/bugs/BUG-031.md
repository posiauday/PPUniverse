## Summary
After #120 was merged, `develop`'s accessibility shard 1 failed once. The Chromium keyboard check for `password-reset-weak` at 1280 px reported every header control as "no keyboard route reached". The same check passed on every PR that day.

## Cause
After a failed save, the reset form moves focus to the password field in an effect, which runs just after the browser paints the error. The gate state waited only for the error text, so the keyboard walk could start in between. When focus then moved, the walk carried on from the password field and missed everything above it. This is the same race as BUG-028, in a different form. Faster first paints (#120 inlines the stylesheet) make the gap more likely.

The app behaves correctly: focus does land on the field with the problem.

## Fix
Six gate states whose error moves focus after it renders now wait until focus has landed, which also checks the behaviour the forms promise (WCAG 2.4.3, 3.3.1):
- `signin-validation-error` and `signin-send-failed`: the email field
- `signin-password-missing` and `signup-weak-password`: the password field
- `password-confirm-expired`: the new heading
- `password-reset-weak`: the new-password field

Checked locally: those six states pass the page matrix and the keyboard check in Chromium, Firefox and WebKit. A first parallel run failed three times while seeding, because the local PGlite database can't handle two workers; one worker passed.

## Expected behavior
The gate measures each state after the page has settled, including where focus ends up.

## Accessibility impact
- [x] None for readers. The forms already moved focus correctly; only the check's timing changed.
