Follows `planning/github/04-bug-template.md`. Found while measuring the accessibility baseline for MVP-023.

## Summary
The sign-in page (`apps/web/app/signin/page.tsx`, a client component) has four accessibility problems: the error message does not identify the field or the problem; keyboard focus is dropped to `<body>` after submitting; the page is entirely unstyled; and its title is the site name only.

## Severity
- [x] P2 — degraded core journey (sign-in is how every user creates an account and returns)

## Affected requirement / feature
- NFR-001. WCAG 2.2 success criteria 3.3.1 Error Identification (A), 3.3.3 Error Suggestion (AA), 2.4.3 Focus Order (A), 2.4.2 Page Titled (A). The unstyled presentation is a design-system conformance gap (`docs/05`), not on its own a definite success-criterion failure.
- Delivered by MVP-002.

## Environment
Local dev server, Chromium, 2026-09-21. Guest.

## Steps to reproduce
1. Open `/signin`.
2. Click "Send sign-in link" with the email field empty.
3. Observe the message and where focus is.

## Expected behavior
The message names the problem ("Enter your email address" / "Enter a valid email address"), moves or keeps focus so keyboard users can continue, and the page has a descriptive title and usable styling.

## Actual behavior
The only feedback is "Something went wrong sending the link. Please try again." (`aria-invalid` becomes true, but the text does not name the field or cause). After the submit, `document.activeElement` is `BODY` — the button disables itself while the request runs and focus is not restored. The heading renders at body size, the submit button looks like plain text, and `document.title` is "Power Platform Universe".

## Evidence
Real click on the empty required field in the browser; `document.activeElement.tagName` read afterwards; screenshot of the unstyled page. The form has `noValidate`, so no native validation message appears.

## Security or privacy impact
- [ ] None.

## Accessibility impact
- [x] Blocks WCAG 2.2 AA conformance (3.3.1, 3.3.3, 2.4.3, 2.4.2). Apply `type:accessibility`.

## Suggested fix
Validate the email client-side with a specific, associated message; keep focus on the button (use `aria-disabled` instead of `disabled`) or move it to the message/field; add a route-level layout that exports a descriptive title (a client page cannot export metadata); apply the design-system styles. Cover with the MVP-023 sign-in spec.
