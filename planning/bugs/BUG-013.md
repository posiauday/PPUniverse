Follows `planning/github/04-bug-template.md`. Found while running the MVP-023
accessibility CI job (run 4, `e43e1aa`) and confirmed with dedicated failure-evidence
instrumentation (run 5, `a5f44c0`). Decision and criterion: `docs/final-decisions.md`,
"Product-owner decision — MVP-023 run 4 / Firefox failures" (2026-09-21).

## Summary
On `/account/sessions`, revoking a session calls `router.refresh()` (in
`SessionRevokeButton`) to re-fetch the page with the updated session list. During
that refresh, in Firefox, the `<title>` element is briefly removed from `<head>`
entirely — not just emptied — so `document.title` reads `""` for a window spanning
at least from when Next's own route announcer fires through the test's own read.
This happened in 2 of 5 CI runs so far (both Firefox only; Chromium and WebKit have
never shown it); it has not reproduced locally in any engine across dozens of manual
runs.

## Severity
- [x] P3 — minor content or admin issue

Per the accessibility severity rubric (`docs/14-accessibility-testing.md`, decision
Q35): this does not block or substantially impede the core journey step. The revoke
itself completes correctly and is reliably announced through the persistent
`role="status"` region added in MVP-023 F7 (`SessionsHeading`), which does not depend
on `document.title` at all. The impact of the title gap itself is narrow: a
screen-reader user relying specifically on Next's *own* built-in route announcer
(a second, independent announcer from ours) would hear nothing informative during
that window, and a browser tab/window title would be blank if observed at that exact
instant. Recorded as P3 rather than P1/P2; the product owner may reclassify on review.

## Affected requirement / feature
- NFR-001, WCAG 2.4.2 Page Titled (A). Delivered by MVP-002 (`SessionRevokeButton`,
  `router.refresh()`) and exercised by MVP-023 F7/F9 (`SessionsHeading`, the page
  title). Not caused by F7/F9 — the title mechanism (Next's own metadata/head
  management) is not code this repository controls directly.

## Environment
CI (`ubuntu-latest`), production build (`next start`), Firefox 155.0 via Playwright
1.63.0's pinned build, `packages/e2e/tests/a11y/pages.spec.ts`, state
`sessions-after-revoke @ 768px`. Not reproduced locally (Windows, same Firefox build,
many runs) or in Chromium/WebKit in any run.

## Steps to reproduce
1. Sign in with two active sessions on `/account/sessions`.
2. Click "Revoke" on a non-current session.
3. Read `document.title` (or `page.title()`) in the brief window after the DELETE
   request completes and before the refreshed page has fully re-rendered.

Not reliably reproducible on demand; observed twice in five CI runs, Firefox only.

## Evidence (run 5, `a5f44c0`, instrumented — `packages/e2e/src/failure-evidence*.ts`)
Title/announcer trace for the failing test (`sessions-after-revoke @ 768px`,
timestamps are `performance.now()` inside the page, zeroed at the start of the
`page.reload()` navigation that `prepare()` performs before the revoke click):

```json
[
  { "kind": "title", "atMs": 0, "title": "", "via": "initial" },
  { "kind": "title", "atMs": 4, "title": "Active sessions | Power Platform Universe", "via": "title-element" },
  { "kind": "announcer", "atMs": 181, "text": "", "documentTitleThen": "Active sessions | Power Platform Universe" },
  { "kind": "title", "atMs": 182, "title": "Active sessions | Power Platform Universe", "via": "title-element" },
  { "kind": "announcer", "atMs": 522, "text": "Active sessions", "documentTitleThen": "" }
]
```

The last entry is the decisive one: Next's built-in `AppRouterAnnouncer`
(`app-router-announcer.js`) reads `document.title` on every route-tree change and
falls back to the page's `<h1>` text when it is falsy. Its announced text here is
`"Active sessions"` — the bare `<h1>`, not `"Active sessions | Power Platform
Universe"` — read from `document.title` **at that exact moment**, captured
synchronously inside the same DOM-mutation callback that wrote the announcer's own
text. That proves `document.title` was empty when Next's own announcer fired.

Independent corroboration: the page's HTML, captured at test-failure time (right
after the same read that failed), shows `<head>` with **no `<title>` element at
all** — the element was removed, not merely emptied, which is also why neither of
the two independent title-change detectors (a `<title>`-element `MutationObserver`,
and a `document.title` setter override) caught an intermediate "emptied" event: the
element was gone, not mutated.

No console errors or page errors were captured (`failure-console.json`: `[]`).

## Classification against the pre-registered criterion
Applying `packages/e2e/src/title-trace.ts`'s `classifyTitleTrace` (unit-tested,
`packages/e2e/src/title-trace.test.ts`) to the trace above:

```
verdict: "product-defect"
reason: the route announcer fired at 522ms announcing "Active sessions" while
        document.title was "" (empty or bare) at that exact moment
```

This is **PRODUCT DEFECT**, per the fixed rule: "... or if it is empty at the
moment Next's route announcer fires." Not TEST DEFECT: the title was not populated
throughout — an independent, first-party mechanism (Next's own announcer) observed
it empty at the same moment our test did, and the raw HTML snapshot confirms the
element was absent.

## Proposed fix (NOT applied — awaiting approval)
Two candidates; recommend (a):

**(a) A client-side title safety net in `SessionsHeading`.** `SessionsHeading`
already stays mounted across the refresh (its `previousCount` ref and `message`
state must survive it, or the revoke announcement would not work at all — this is
already proven by the existing, passing F7 tests). Add an effect that re-asserts
`document.title` to the known correct value whenever the effect that handles the
revoke announcement runs, using the existing `SITE_NAME` constant
(`apps/web/lib/seo/site.ts`) and a literal page name, so a transient removal of
Next's own `<title>` element is corrected within the same render pass rather than
left empty until Next's own streaming catches up. Minimal, scoped to the one file
already touched by F7.

**(b) Investigate Next.js's own metadata-streaming/Suspense behavior** to find
why `<title>` is removed during a same-route `router.refresh()` and whether a
framework-level opt-out avoids it. Higher effort, may not have an app-level fix
available, and is not obviously "minimal."
