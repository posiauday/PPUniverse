## Summary
Two CI failures so far, on two different assertions, sharing the same shape: a click on
the sign-in page's "Send sign-in link" button appears to produce no effect at all — no
network request, no client-side validation state change.

| Run | Commit | State | What was checked | What happened |
|---|---|---|---|---|
| 4 | `e43e1aa` | `signin-sent @ 320px` | `role="status"` shows "check your email" | Stayed empty; no `/api/auth/*` request after the click (from Playwright's own action trace; this run predates the dedicated evidence capture) |
| 7 | `18b7b46` | `signin-send-failed @ 320px` | The email field's accessible description says "try again" | Stayed empty, `aria-invalid` stayed `"false"`; the failure-evidence network log shows only the initial page load — no `POST /api/auth/signin/email` at all, intercepted or otherwise |

**The correlations, stated plainly because they narrow the search:**
- Both **Firefox only** (chromium and webkit have never shown either).
- Both **at 320px only** (the same states at 375/768/1280px have never failed).
- Both on the **same control** (the "Send sign-in link" button, reached via
  `packages/e2e/src/pages.ts`'s `submitSignIn`, a plain `.click()`).
- Both show the **application's own handler never executing** — not a failed fetch, not
  a slow response, but no sign the click had any effect at all.

Both times, every other state, in every other engine, at every other width, in the
same run, passed. Neither run's server log showed any error.

## Hypothesis under investigation (2026-09-21) — explicitly unproven, not the cause

React attaches its event listeners at the root container it was given, not at
individual elements. If the button is replaced or detached between the locator
resolving and the click being dispatched — plausibly triggered by the `fill()`-induced
re-render, amplified by narrow-viewport reflow and CI timing — the click would dispatch
to an orphan node, never reach React, and produce no validation and no request. This is
consistent with every symptom observed in runs 4 and 7.

**This is a candidate to be confirmed or eliminated by evidence, not a conclusion.**
The instrumentation in `packages/e2e/src/signin-click-diagnostics.ts` was extended
specifically to test it: two snapshots of the same button (right after the locator
resolves, and again immediately before the click, after `fill()`), compared for node
identity (a `WeakMap`-based check: is it literally the same element object, or a
different one), connectedness, and layout; and two tiers of event listener (`document`,
and React's own root container if it can be found), so a click reaching `document` but
never reaching the root is a distinguishable, visible fact rather than an assumption.

## Runs 8 and 9 voided as evidence (2026-09-22, direct product-owner instruction: "Run 10

**Runs 8 and 9 carry NO evidentiary weight for this signature, in either direction.**
Both runs' diagnostics threw during `evaluate()` serialization
(`ReferenceError: DOC_EVENTS_KEY is not defined`, fixed in `8d4c724`) — a green result
from a broken instrument is not evidence of absence, and neither run's data is usable to
support or eliminate the hypothesis below. Run 10 is the first run capable of testing it,
and only once the self-check below has itself passed in a real browser.

**Self-check required before any classification, and not yet satisfied by run 10 as
pushed.** `failure-evidence.ts`'s `attachOnFailure` returns immediately on a passing
test, so on any run where every sign-in state passes, no click-diagnostics evidence is
ever extracted from the browser — there is nothing to inspect, and this is true
regardless of run 10's outcome unless it happens to fail on a sign-in state specifically
(and even then, only the `fill()`-affected snapshots are captured, not a clean
untouched-element control). A dedicated self-check
(`packages/e2e/tests/a11y/harness-smoke.spec.ts`, "the click-diagnostics instrument
proves itself in a real browser") was added to close this gap: it asserts, unconditionally
and independent of the sign-in flow, that (a)/(b) the same untouched element reports the
same identity token across two separate `evaluate()` calls — provable only in a real
browser, since if the identity store were rebuilt inside the function body instead of
read from a persistent `window` global this would fail every time; (c) a genuinely
different element reports a different token; and (d) a real click is captured at both
`document` and React's own root container, not only at the clicked element. This is test
logic only, no product code, no suite configuration change, and is the next commit after
run 10.

## Run 12: the self-check itself failed — an instrument defect, not a BUG-014 finding
(2026-09-22)

Per section 4 of "Run 10 disposition" ("FAILS ON THE DIAGNOSTICS THEMSELVES: treat as an
instrument defect, not a product or test finding. Fix the instrument only. Do not
classify BUG-014 from that run"): the self-check added to close the section-2 gap
(`harness-smoke.spec.ts`) failed in **all three engines**, but every actual sign-in
state (`signin-validation-error`, `signin-send-failed`, `signin-sent`) **passed
cleanly** in the same run — the signature did not recur, and this failure has no
bearing on it either way.

**Root cause, confirmed by reading Next.js's own client source, not guessed:**
`installClickEventTracer`'s scan for React's root-container marker checked only
`document.querySelectorAll("*")` (Element nodes). Next.js's App Router hydrates directly
onto `document` itself —
`node_modules/next/dist/client/app-index.js`: `const appElement = document;` then
`hydrateRoot(appElement, ...)` — and `document` is a `Document`, not an `Element`, so
`querySelectorAll("*")` can never include it. The scan therefore reported "not found" in
every engine, 100% reproducibly (not flaky — a wrong assumption, deterministic every
time), and the self-check's `rootContainer.found` assertion caught exactly that.

**Fixed** (`packages/e2e/src/signin-click-diagnostics.ts`, test logic only): the scan now
also checks `document` itself alongside the element scan. Verified locally
(typecheck/lint/format all clean) and by extending the serialization simulation used for
the run-9 fix: a `__reactContainer$`-prefixed property set directly on a jsdom
`document` (simulating what React's real `hydrateRoot(document, ...)` does, since jsdom
does not run real React) is now correctly found, reported as `"document"`, and a
dispatched click is captured at both the document-level and root-level listeners — which
are the same node in this app, by its own architecture, a fact now documented in the
code rather than assumed.

This also means: in this application specifically, "reached `document`" and "reached
React's own root" are the same fact, since React's root IS `document`. Control (d) from
"Run 10 disposition" — distinguishing a click reaching `document` from one reaching
React's root — still holds as designed; it simply resolves to the same listener here,
which is itself useful, confirmed information about this app's hydration model, not a
weakening of the control.

## Reclassification (2026-09-22, direct product-owner instruction: "BUG-014
recurrence"): run 15's evidence is not ambiguous between test/product defect — it is
**UNREADABLE**, because the self-check proves the mechanism works in general, but does
NOT prove the listener installed on the sign-in page was still attached to the live
document specifically at the moment of the click. Every symptom above (zero captured
events at any listener, zero network request, yet a structurally sound, hit-testable
button) is equally consistent with "the document was silently replaced between install
and click, so the listener that captured nothing was no longer the live one" as it is
with "the click genuinely reached a live, listening application and nothing happened."
Run 15's instrumentation cannot distinguish these, because it never checked whether its
own observer was still alive at the moment that mattered.

**New hypothesis (2026-09-22), explicitly unproven, not the cause:** the document was
replaced between listener installation and click dispatch — plausibly a native HTML
form submission that was not prevented because the React submit handler had not
attached (e.g. a hydration race). A listener installed via `evaluate()` dies with the
document it was installed on; route interception registered against the prior
browsing context would not fire for a request made after a fresh navigation of the
same page. Observable result: a valid, connected, correctly-positioned button; a
successful physical click; no captured event; no matching network request; and no
*redirect* in the ordinary sense, because a same-URL native form reload is not a
redirect and would not necessarily register as one in evidence that was only ever
designed to detect the latter. **If this is true, the "product defect" and the
"observation failure" are the same event, not alternatives** — a form falling back to
uncontrolled native submission because its handler never attached would itself be the
real defect, and would also explain why every diagnostic instrument built to observe it
from inside the (replaced) document came back empty.

**Superseded classification criterion.** The criterion at the "Decision" section above
(TEST DEFECT / PRODUCT DEFECT / third case, based on node connectivity, identity and
box stability) is retained for its history but is **superseded** for any future
evidence by the criterion below, which accounts for observer liveness directly:

- **PRODUCT DEFECT** if a native submit fired unprevented, or a navigation occurred
  that the application should have prevented. A form that falls back to native
  submission because its handler is not attached is a real defect regardless of
  Playwright's own involvement.
- **TEST DEFECT** if the observer was dead at click time for a reason attributable to
  harness ordering (listener installed against a stale context, or installed after a
  navigation already in flight) and the application behaved correctly. The remedy is
  fixing the harness's ordering, stated as such.
- **STILL UNREADABLE** if the observer was demonstrably alive, the document was not
  replaced, no navigation occurred, no native submit fired, and the click still
  produced nothing observable at document capture.

**Round 2 instrumentation authorized — test logic only, the LAST investigation round
inside MVP-023** (direct product-owner instruction, "BUG-014 recurrence"):
(a) observer liveness — an install-time token on `window`, read back immediately
before AND immediately after click dispatch; an evaluate() call that itself throws
because "the execution context was destroyed" is treated as direct, positive evidence
of a navigation, not merely a missing data point; (b) document identity — the same
token mechanism, since a document teardown cannot be survived by anything stored on
its `window`; (c) navigation events — Playwright's own `framenavigated`/`load`/
`domcontentloaded` page events, subscribed for the duration of the interaction and
recorded with timestamp and URL, including same-URL navigations, attached on failure as
`failure-navigation.json`; (d) native submit — a SEPARATE bubble-phase `submit`
listener at `document` (alongside the existing capture-phase one), specifically so
`event.defaultPrevented` is read at the point in propagation where it is meaningful —
document is the outermost point in the tree, so a bubble-phase listener there runs
last among document-reachable listeners, after any bubble-phase handler (including
React's default delegation) has already had its chance to call `preventDefault()`; a
capture-phase read would show `false` even in the normal, working case, since it fires
before bubble-phase handlers run; (e) interception context — `interceptSignInSend` now
tracks its own invocation count directly (a closure counter incremented inside the
route handler itself), rather than inferring "was the interceptor reached" solely from
the network log.

Per the same instruction, disposition after this round is decided in advance and this
record's own investigation does not reopen regardless of outcome: PRODUCT DEFECT is
fixed under this story; TEST DEFECT is fixed (harness ordering only) under this story;
STILL UNREADABLE proceeds to completion with the full evidence, eliminated hypotheses,
and future instrumentation needs recorded, this record staying open, monitor-only,
permanently instrumented. No further investigation round is authorized inside MVP-023
after this one; a post-merge recurrence is a new round under new authorization.
