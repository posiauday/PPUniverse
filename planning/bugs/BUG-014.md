## Summary
Two CI failures so far, on two different assertions, sharing the same shape: a click on
the sign-in page's "Send sign-in link" button appears to produce no effect at all — no
network request, no client-side validation state change.

| Run | Commit | State | What was checked | What happened |
|---|---|---|---|---|
| 4 | `e43e1aa` | `signin-sent @ 320px` | `role="status"` shows "check your email" | Stayed empty; no `/api/auth/*` request after the click (from Playwright's own action trace; this run predates the dedicated evidence capture) |
| 7 | `18b7b46` | `signin-send-failed @ 320px` | The email field's accessible description says "try again" | Stayed empty, `aria-invalid` stayed `"false"`; the failure-evidence network log shows only the initial page load — no `POST /api/auth/signin/email` at all, intercepted or otherwise |

**The correlations, stated plainly because they narrow the search:**
- Both **Firefox only** (chromium and webkit have never shown either).
- Both **at 320px only** (the same states at 375/768/1280px have never failed).
- Both on the **same control** (the "Send sign-in link" button, reached via
  `packages/e2e/src/pages.ts`'s `submitSignIn`, a plain `.click()`).
- Both show the **application's own handler never executing** — not a failed fetch, not
  a slow response, but no sign the click had any effect at all.

Both times, every other state, in every other engine, at every other width, in the
same run, passed. Neither run's server log showed any error.

## Decision (2026-09-21, direct product-owner instruction: "Run 7 failure / sign-in
submit signature", extended by "Run 8 disposition")
- **Instrumentation authorized, applied, and then extended twice** (test logic only, no
  product code, no suite configuration change): `packages/e2e/src/signin-click-diagnostics.ts`,
  wired into `submitSignIn` in `pages.ts` and read by `failure-evidence.ts`. On any
  future failure of a sign-in submit state, it now captures: two snapshots of the
  button — right after the locator resolves, and again immediately before the click, so
  the window `fill()`'s re-render opens is what gets compared, not something before it —
  each recording node identity (a `WeakMap`-based check: the same element object, or a
  different one), `isConnected`, hydration (a React fibre property), visibility,
  pointer-events, z-index, bounding rectangle, and its own hit test
  (`document.elementFromPoint` against that exact element and its own just-measured
  centre); the delta between the two snapshots' bounding boxes; a capture-phase event
  log at `document` AND, if it can be found, at React's own root container, so an event
  reaching one but not the other is a visible, distinguishable fact; the CSS Font
  Loading API's `document.fonts.status` at each snapshot; and the Node-side timestamp
  gap between the route interception being registered and the click being issued.
- **Fixed classification criterion, decided in advance of any evidence, extended:**
  - **TEST DEFECT** if `isConnected` is false at dispatch, or node identity changed
    between the two snapshots, or the bounding box shifted between them. The remedy is
    the test's own re-resolution/stability handling, stated as such — not a product fix.
  - **PRODUCT DEFECT** if the node was connected, its identity stable, its box stable,
    the click arrived at `document` and at React's own root, and the application still
    did nothing. A control that accepts a genuine click and remains inert is a real
    defect.
  - **A third case** — the evidence contradicts itself, or the event arrived at
    `document` but not at the React root, or it fits neither bucket — stops for a
    report rather than being forced into either.
  - **Ambiguous evidence** also stops for a report rather than taking the cheaper
    reading.
- **Monitor, do not fix.** No fix is proposed or applied without fresh, evidence-backed
  classification and explicit approval. No retry, wait, timeout change, or conditional
  skip.
- **Does not block MVP-023.**
- **Merge position:** the instrumentation commit is the next sample (not a separate
  documentation-only push obtained purely to get a fresh CI run — the standing rule
  against re-pushing unchanged code until a check goes green applies here too). If that
  run is green, merge is permitted once the full completion rule holds. If it fails on
  this same signature, the new evidence is classified per the criterion above and
  reported before any fix. If it fails on something new again, that is treated as
  another new finding — instrumented, classified, reported — not fixed under this
  authorization.
- **This record stays open past merge**, monitor-only, with the instrumentation
  permanently in place.

## Hypothesis under investigation (2026-09-21) — explicitly unproven, not the cause

React attaches its event listeners at the root container it was given, not at
individual elements. If the button is replaced or detached between the locator
resolving and the click being dispatched — plausibly triggered by the `fill()`-induced
re-render, amplified by narrow-viewport reflow and CI timing — the click would dispatch
to an orphan node, never reach React, and produce no validation and no request. This is
consistent with every symptom observed in runs 4 and 7.

**This is a candidate to be confirmed or eliminated by evidence, not a conclusion.**
The instrumentation in `packages/e2e/src/signin-click-diagnostics.ts` was extended
specifically to test it: two snapshots of the same button (right after the locator
resolves, and again immediately before the click, after `fill()`), compared for node
identity (a `WeakMap`-based check: is it literally the same element object, or a
different one), connectedness, and layout; and two tiers of event listener (`document`,
and React's own root container if it can be found), so a click reaching `document` but
never reaching the root is a distinguishable, visible fact rather than an assumption.
