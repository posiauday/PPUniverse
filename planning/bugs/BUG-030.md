## Summary
Found by the accessibility gate on PR #112: `/admin/deletion-requests` returned 500 once in Firefox, with "DeletionRequest has no events — expected at least SUBMITTED".

`listActiveDeletionRequests` reads twice: each request's latest event, then the active requests with their full history. The two reads aren't one snapshot. If a request is deleted between them (its events are deleted first), the second read returns it with no events, and `currentDeletionRequestState` throws, failing the whole page.

In the gate, other test workers reset their own deletion requests (events, then the request, as separate statements) while the admin queue, which lists every user's requests, was loading. The same window exists in production when a request is deleted, though it's much rarer there.

## Severity
- [x] P3: the admin queue fails to load until it's reloaded. No data is lost or exposed.

## Fix
- `listActiveDeletionRequests` (`packages/adapters/privacy/src/privacy-repository.ts`) skips a request that comes back with no events: it's being deleted, so it's no longer in the queue.
- The gate's fixtures (`packages/e2e/src/seed.ts`) reset and create deletion requests in one transaction each, so other workers never see half of a change.
- Regression test: `privacy-repository.test.ts` replays the race and fails without the fix.
