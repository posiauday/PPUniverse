Follows `planning/github/04-bug-template.md`. Found while implementing MVP-023.

## Summary
`SessionRevokeButton` sets `disabled` on the Revoke button while its request runs. A focused element that becomes disabled drops keyboard focus to the document body. MVP-023 F7 fixes the success path (the row disappears and focus moves to the heading). When the DELETE request **fails**, the button is re-enabled and an error message appears, but focus is still on the body.

## Severity
- [x] P3 — minor content or admin issue (accessibility rubric Q35: **P3**, an error path outside a core-journey step)

## Affected requirement / feature
- NFR-001; WCAG 2.4.3 Focus Order. Delivered by MVP-002 (`apps/web/app/account/sessions/SessionRevokeButton.tsx`).

## Steps to reproduce
1. Sign in with two sessions and open `/account/sessions`.
2. Make the DELETE request fail (for example stop the API), focus Revoke with Tab and press Enter.
3. Read `document.activeElement` after the error appears.

## Expected behavior
Focus stays on the Revoke button (or moves to the error message), and the error is announced (it already is: `role="alert"`).

## Actual behavior
Focus is on the body; a keyboard user has to Tab from the top of the page again.

## Security or privacy impact
- [x] None.

## Accessibility impact
- [x] Keyboard focus lost on an error path. Apply `type:accessibility`.

## Suggested fix
Use `aria-disabled` instead of `disabled` (the same one-attribute change MVP-023 F6 made on the sign-in button) and ignore clicks while it is set; add a regression test that fails a stubbed request.
