Follows `planning/github/04-bug-template.md`. Found while implementing MVP-023.

## Summary
`packages/db/src/index.ts` (delivered by MVP-002) only caches its Prisma client on `globalThis` when `NODE_ENV !== "production"`:

```ts
function getPrisma(): PrismaClient {
  if (globalThis.__ppuPrisma) return globalThis.__ppuPrisma;
  const client = createPrismaClient();
  if (process.env["NODE_ENV"] !== "production") {
    globalThis.__ppuPrisma = client;
  }
  return client;
}
```

The exported `prisma` is a lazy Proxy that calls `getPrisma()` on **every property access**. In a production build nothing is ever cached, so every query constructs a new `PrismaClient` with a new `pg` pool. Connections are only closed after the pool's idle timeout (10 s by default), so a burst of requests leaves one live connection per query and Postgres refuses new ones at its `max_connections` (100 by default) with "sorry, too many clients already" (Prisma `P2037` / `TooManyConnections`). The affected requests return HTTP 500. In development and test the client is cached, which is why nothing caught this before: tests run with `NODE_ENV=test` and `next dev`, and no production deployment exists yet.

## Severity
- [x] P1 — checkout or download outage (any database-backed page or API would fail under modest concurrent load in production)

No production deployment exists, so nothing has been exposed.

## Affected requirement / feature
- Reliability of every database-backed route (catalog, product, search, sign-in, sessions, health). Delivered by MVP-002.

## Environment
- Production build (`next build` then `next start`, Next.js 16.3.5, `NODE_ENV=production`); Postgres 17 with default settings.

## Steps to reproduce
1. Run against a local Postgres, from `packages/e2e`: a script that imports `@ppu/db`, runs 40 sequential `prisma.category.count()` calls, then counts `pg_stat_activity` rows for the database.
2. Run it with `NODE_ENV=development`, then with `NODE_ENV=production`.

## Expected behavior
One shared client and a bounded pool regardless of `NODE_ENV`.

## Actual behavior
Measured 2026-09-21:
- `NODE_ENV=development`: 40 queries, **1** open connection, client cached on `globalThis`.
- `NODE_ENV=production`: 40 queries, **41** open connections, client not cached.

## Evidence
The first CI run of the MVP-023 accessibility job (run 35665652208) served the production build to three parallel browser workers and failed three Chromium tests (Firefox and WebKit passed every test): an HTTP **500** where a 404 was expected, a category page with no products, and a session revoke whose DELETE failed. The server log for that job shows "Too many database connections opened: sorry, too many clients already" with Prisma `P2037` and `DriverAdapterError: TooManyConnections` on `prisma.category.findUnique`, `prisma.product.findFirst` and `prisma.session.delete`. The accessibility tests are not at fault; they exposed the defect.

## Security or privacy impact
- [x] Availability: an unauthenticated request rate can exhaust the database's connections and make every database-backed route return 500. No data exposure.

## Accessibility impact
- [x] None directly.

## Suggested fix
Cache the client on `globalThis` in every environment (drop the `NODE_ENV` condition in `getPrisma`), and bound the pool explicitly. Add a regression test that fails before the fix: a unit test that, with `NODE_ENV=production`, two accesses to `prisma` construct the client once; and a database-gated integration check that many sequential queries hold at most a pool's worth of connections.

## Why it is not fixed in MVP-023
Changing `@ppu/db` changes MVP-002 behavior, which the MVP-023 authorization reserves (only the Q37 fixes may touch completed stories). Recorded as open question 43; MVP-023 is Blocked until the product owner decides.
