## Summary
Found by the product owner: a signed-out reader who selects Copy YAML on a sign-in-to-copy component is asked to sign in. After signing in they land on their account page (`/account/sessions`), not back on the component, so they have to find it again.

## Cause
The component page (and the guide comments and Learn pages) already send readers to `/signin?callbackUrl=/components/<slug>`. The sign-in page ignored `callbackUrl`: the password sign-in, the emailed sign-in link and Continue with Google all used the fixed `SIGNED_IN_PATH`.

## Fix
- `continuePath()` in `apps/web/lib/password-client.ts` reads `callbackUrl` from the sign-in page's address. It returns it when it's a path on this site, and `SIGNED_IN_PATH` otherwise. It refuses other sites (`https://…`, `//host`, `/\host`), so it can't be used as an open redirect, and it refuses `/signin` itself.
- The sign-in page uses it for all three ways to sign in. A new account from an emailed link or Google still goes through `/account/welcome` (the Terms) first: NextAuth passes the same `callbackUrl` on, and the welcome page already continues to it.
- Tests: `apps/web/lib/password-client.test.ts`.

**Hardened after CodeQL** (`js/client-side-unvalidated-url-redirection` on the PR): the first check only looked at the text's first characters, so `/%09/host` (a slash, a tab, a slash) got through, and browsers drop the tab and read `//host`, another site. `continuePath()` now resolves the address against the site's own origin and keeps it only if it stays there, returning the parsed path. Tests cover the tab, newline and backslash forms.

## Not in this fix
A brand-new **password** account confirms its email through a link, and that link doesn't carry the page it started from, so it still lands on the account. Tracked as TD-033.

## Expected behavior
Sign in from a component's Copy YAML and you're back on that component, signed in, ready to copy.
